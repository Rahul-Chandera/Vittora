# A2.1 — XL Dynamic Type contrast debt (1.4.1 fast-follow)

**Branch:** `feature/a2.1-xl-contrast-debt` · **PR into:** `develop` ·
**Review tier: B** · **Deferred from A2 (#155) by explicit release decision.**

## Why this is a separate task

A2 (#155) expanded the accessibility audit to run `performAccessibilityAudit`
at `AccessibilityXL` Dynamic Type across every surface. That expansion is
**new coverage** — none of these audits existed on `develop` before #155.
It surfaced pre-existing WCAG AA contrast misses on secondary/tertiary chrome
that had been shipping unaudited since 1.0.

For the 1.4.0 release the decision (2026-07-22) was: ship the confirmed A2
work — Payees audit-navigation fix, the three originally-caught XL contrast
fixes (New Transaction, and the shared `textSecondary`/`textTertiary` token
strengthening), and the **core-flow** XL audit coverage — and defer the newly
added **surface** XL audits, together with their fixes, to 1.4.1. This stages
the expansion of the bar rather than lowering an existing one: the deferred
tests are skipped **visibly**, with this document referenced in the skip
reason, not deleted or weakened.

## Scope

1. **Remove the `XCTSkip` from each test above** and get it green at
   `AccessibilityXL`.
2. **Fix at the colour-token / component level, not per screen.** These repeat
   across surfaces, so most are likely a small number of shared pairings
   (secondary text on secondary background, decorative status colours). Prefer
   one token fix that clears several audits over eight local patches.
3. **Prioritise `testTaxSurfacesAccessibilityAudit` (India).** Devanagari has
   heavier glyph weight and different metrics than Latin, so a pairing that
   clears AA in English can fail in Hindi. It is the only failure on a launch
   storefront's primary path.
4. **Verify every token change against all themes** — light, dark, OLED black,
   and OLED secondary surfaces. Do not fix XL and regress a standard size, and
   do not fix one theme and regress another. This is why it is a deliberate
   task and not a rushed patch: the shared tokens touch every screen.

## Hard rules (carried from A2)

Never disable, narrow, or suppress an audit category; never weaken an
assertion; never alter demo/seed data so a failing element stops rendering
(AGENTS.md house rule 9). If a specific element is a genuine Apple false
positive, narrow the exclusion to that element and justify it in the PR — do
not broaden the existing decorative-mark exclusion.
